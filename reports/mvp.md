# Отчёт: MVP (Задание 2)

## Что сделано

Реализован кулинарный ассистент в виде Telegram-бота с REST API. Пользователь описывает продукты или ситуацию ("романтический ужин"), бот предлагает рецепты с оценкой стоимости докупки.

## Технический стек и обоснование

**Python + FastAPI** — легковесный async-фреймворк, хорошо подходит для I/O-heavy задач (запросы к SQLite, ChromaDB, OpenAI API). Альтернатива Flask — синхронная, пришлось бы городить thread pool. Django — избыточен.

**aiogram 3** — наиболее актуальный async-фреймворк для Telegram Bot API. Поддерживает long polling из коробки, что проще webhook для учебного проекта.

**SQLite + FTS5** — нулевая инфраструктура, достаточная производительность для 80K рецептов. FTS5 даёт полнотекстовый поиск по ингредиентам на уровне Postgres-решений для нашего объёма. Альтернатива (PostgreSQL) требует отдельного сервера.

**ChromaDB** — embedded векторная БД, запускается в процессе без сервера. Для 80K рецептов индекс умещается в ~200MB на диске. Альтернативы (Weaviate, Qdrant) требуют отдельного контейнера.

**intfloat/multilingual-e5-small** — 118MB, работает на CPU, поддерживает русский и английский в едином векторном пространстве. Это ключевое: пользователь пишет на русском, рецепты на английском. Более крупные модели (e5-large, bge-m3) дали бы лучшее качество, но неприемлемы на CPU для учебного проекта.

**OpenAI GPT-4o-mini** — самая дешёвая модель с достаточным качеством для перевода и форматирования рецептов. ~$0.003 за запрос при среднем промпте 2K токенов. Поддержка OpenRouter позволяет работать из РФ без VPN.

## Архитектурные решения

**Два вида поиска** (FTS5 + семантический) запускаются параллельно через `asyncio.gather`, результаты объединяются с дедупликацией по ID. FTS5 хорошо работает для точных запросов по ингредиентам, ChromaDB — для сценарных запросов ("что-то лёгкое после тренировки"). Комбинация покрывает оба случая.

**Direct answer mode**: если topK-рецепт имеет score выше порога (`direct_answer_threshold=0.9`), ответ формируется без вызова LLM — быстрее и дешевле.

**Сессии в памяти**: история диалога хранится в dict по `chat_id` с TTL 30 минут. Простое решение без Redis. При перезапуске сервера история теряется — для учебного проекта приемлемо.

**Логирование в SQLite**: все диалоги (`user_message`, `bot_response`) и фидбэк (👍/👎) пишутся в таблицу `logs` для ручного анализа качества.

## Сложности

**Формат данных Food.com** — ингредиенты и шаги хранятся в R-стиле (`c("item1", "item2")`), а не JSON. Написан парсер через regex с escaping.

**Маппинг языков** — рецепты на английском, запросы на русском. Решено через multilingual embedding для векторного поиска, и через LLM-перевод при генерации ответа. FTS5-поиск работает напрямую по английским ингредиентам; если пользователь пишет по-русски, FTS5 не находит совпадений и полагаемся на семантику.

**Производительность embedding** — первый запрос после старта медленный: модель загружается лениво. Решено опциональным preload при старте.

**Docker healthcheck** — FastAPI блокировался на preload модели при старте, healthcheck не отвечал. Решено переводом preload в фоновый asyncio-таск (актуально для infra-ветки).
