# Отчёт: MVP (Задание 2)

## Что сделано

Разработан MVP кулинарного ассистента в формате Telegram-бота с REST API. Пользователь может указать, какие продукты у него есть, или описать желаемый сценарий. В ответ система подбирает подходящие рецепты из базы Food.com, переводит их на русский язык и показывает примерную стоимость.
Основной пайплайн работает так: пользовательский запрос переводится на английский, затем выполняется поиск по базе рецептов двумя способами — по ингредиентам и по смыслу. После этого результаты объединяются, и LLM формирует итоговый ответ на русском языке в удобном формате.

## Стек и почему так

В качестве основного языка использовался Python, backend реализован на FastAPI. Это решение хорошо подошло для проекта, поскольку позволяет удобно работать с асинхронными запросами.

Для Telegram-бота использовался aiogram 3. Он асинхронный и удобен для разработки в учебном окружении.

Для хранения рецептов была выбрана SQLite с поддержкой FTS5. Этого достаточно для MVP, так как база рецептов помещается небольшая, а полнотекстовый поиск работает быстро и не требует отдельной инфраструктуры.

Для семантического поиска использовалась ChromaDB как векторная база данных. Индекс 500к рецептов ~500MB, она также не требует отдельного сервера, что удобно для прототипа.

В качестве модели эмбеддингов была выбрана intfloat/multilingual-e5-small — 118MB, подходит под CPU-only задачи, поддерживает русский + английский в одном пространстве. Для нас это критично: пользователь пишет на русском, рецепты на английском.

Для генерации ответов и перевода запросов использовалась модель OpenAI GPT-4o-mini через OpenRouter. ~$0.003 за запрос. OpenRouter нужен потому что из РФ напрямую OpenAI API не работает.

## Как устроен поиск

Два поиска запускаются параллельно через asyncio.gather:

- FTS5 — классический полнотекстовый поиск по ингредиентам, пользователь перечисляет конкретные продукты ("курица, рис, соевый соус").
- Семантический (ChromaDB) — поиск по смыслу через embeddings для сценарных запросов ("что-то лёгкое после тренировки").

Результаты объединяются с дедупликацией по ID рецепта. Если оба поиска нашли один и тот же рецепт — берём максимальный score. Рецепт проходит если score выше порога.

Перед поиском запрос переводится на английский через gpt-4o-mini. Перед поиском запрос переводится на английский язык. Это улучшает качество поиска, так как рецепты в базе хранятся на английском.

## Сессии и история

Для каждого чата хранится краткая история сообщений (dict по chat_id), которая передаётся в LLM и позволяет поддерживать контекст диалога. TTL 30 минут, максимум 10 сообщений. 

## Сложности

- Формат Food.com. Ингредиенты хранятся в R-стиле: c("item1", "item2"). Написали парсер с обработкой экранирования кавычек.

- Маппинг языков. Первая версия использовала ручной словарь из ~260 слов (ru $\rightarrow$ en) + pymorphy3 для лемматизации. Быстро выяснилось что это ненадёжно: "карри" не было в словаре, "говяжий фарш" не лемматизировался (pymorphy3 работает с отдельными словами). Заменили на перевод через LLM — проще и надёжнее, ценой +200-400ms на запрос.

- Скоринг. FTS5 rank и косинусное расстояние живут на разных шкалах. FTS даёт score 0.05–0.15, семантика 0.2–0.9. Один threshold на обоих не работал — FTS-результаты вырезались. Перешли на OR-фильтрацию: рецепт проходит если хотя бы один источник дал score выше порога.

- LLM-промпт. Первая версия была слишком строгой — LLM отвечал "рецептов нет" даже когда были частичные совпадения. Переписали правила: если рецепты в контексте есть — предложи ближайшее, поясни что совпало.
