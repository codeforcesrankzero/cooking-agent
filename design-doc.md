# Design-Doc: Cooking Agent — LLM-based кулинарный помощник

## 1. Контекст проекта

### 1.1 Бизнес-задача

**Проблема:** большинство кулинарных сервисов (Поварёнок, Eda.ru, SuperCook) работают «от рецепта к списку покупок». Пользователь должен сам выбрать что хочет приготовить, а потом идти в магазин. Обратный сценарий — «у меня есть курица, картошка и лук, что приготовить?» — поддерживается плохо: обычно это фильтр по ингредиентам без понимания контекста, без подсказок по докупке и без учёта предпочтений.

**Решение:** LLM-агент, который:

1. Принимает список имеющихся продуктов и предлагает рецепты.
2. Понимает контекстные запросы: «ужин на свидание», «что-то лёгкое для спортивной недели», «быстрый завтрак» — не только поиск по ингредиентам, но и по смыслу.
3. Подсказывает, какие продукты нужно докупить и сколько это примерно будет стоить.
4. Учитывает предпочтения: кухня, сложность, время готовки, диетические ограничения.

**Почему чат-бот, а не просто фильтр на сайте:**
Фильтр по ингредиентам (как на SuperCook) не понимает контекст: «хочу что-то праздничное» или «быстро и сытно после тренировки» — это не набор ингредиентов, а намерение. Для интерпретации таких запросов нужна связка семантического поиска + LLM. Кроме того, бот может вести диалог: уточнять, предлагать альтернативы, считать стоимость — фильтр на это не способен.

**Критерии успеха:**

- Пользователь получает релевантные рецепты по списку продуктов.
- Бот корректно определяет недостающие ингредиенты и даёт адекватную оценку стоимости.
- Семантический поиск возвращает осмысленные результаты для сценарных запросов («романтический ужин», «спортивный обед»).
- Ответы приходят в рамках разумного времени (< 15 секунд).
- Положительная обратная связь от тестовой группы (одногруппники, преподаватель).

### 1.2 Целевая аудитория и пользователи

- **Кто:** студенты, люди, которые хотят готовить из того, что есть дома.
- **Сценарии использования:** текстовый чат (Telegram-бот).
- **Нагрузка:** учебный проект — до нескольких десятков пользователей одновременно, пиковая нагрузка не критична.

**Цена ошибки:** низкая. Худший сценарий — бот предложит неудачный рецепт или неточную цену. Это не критично: пользователь не потеряет деньги и не пострадает (в отличие от медицинского или финансового бота). Репутационный риск минимален — учебный проект, не коммерческий продукт.

### 1.3 Ограничения и допущения

**Ограничения:**

- Не является медицинским советником — не даём рекомендации по аллергиям / противопоказаниям с гарантией.
- Цены на продукты ориентировочные — парсятся с одного источника (каталог Перекрёстка), могут отличаться от реальных цен.
- Бот не обрабатывает фото/видео, только текст.
- Не отвечаем на вопросы, не связанные с кулинарией, — вежливо перенаправляем.

**Допущения:**

- Пользователь вводит продукты текстом на русском языке.
- OpenAI API доступен, бюджет ~$10–15 на проект.

## 2. Архитектура решения

### 2.1 Общая схема

```
Пользователь (Telegram / Web)
        │
        ▼
   Чат-интерфейс (бот)
        │
        ▼
   Backend (Python, FastAPI)
        │
        ├──► Парсинг запроса: извлечение продуктов, намерения, контекста
        │
        ├──► Поиск рецептов (два пути):
        │    ├──► По ингредиентам (SQLite FTS5)
        │    └──► По смыслу / сценарию (ChromaDB, vector search)
        │         │
        │         ▼
        │    Ранжирование и отбор топ-N рецептов
        │
        ├──► Справочник цен (SQLite, автообновление)
        │         │
        │         ▼
        │    Расчёт стоимости докупки
        │
        └──► LLM (OpenAI API, GPT-4o-mini)
                  │
                  ▼
           Генерация финального ответа
                  │
                  ▼
           Ответ пользователю
```

**Компоненты:**


| Компонент           | Роль                                                        |
| ------------------- | ----------------------------------------------------------- |
| Telegram-бот        | Приём сообщений, отправка ответов (aiogram)                  |
| Backend (FastAPI)   | Обработка запросов: парсинг → поиск → расчёт → генерация     |
| База рецептов (SQLite) | Хранение рецептов, FTS5-поиск по ингредиентам             |
| Векторный индекс (ChromaDB) | Семантический поиск по сценарию/контексту запроса    |
| Справочник цен (SQLite) | Обновляется скриптом парсинга                            |
| Скрипт парсинга цен | httpx + BeautifulSoup, запуск по cron                       |
| LLM (GPT-4o-mini)  | Генерация ответа на естественном языке                       |


### 2.2 Хранилище знаний

**Источники рецептов:**

- [Food.com Recipes and Reviews](https://www.kaggle.com/datasets/irkaal/foodcom-recipes-and-reviews) — ~80K рецептов, поля: `name`, `ingredients`, `steps`, `minutes`, `tags`, `nutrition`. Английский язык.
- [RecipeNLG](https://www.kaggle.com/datasets/paultimothymooney/recipenlg) — 2M+ рецептов, поля: `title`, `ingredients`, `directions`, `NER` (извлечённые сущности). Английский язык.

Рецепты на английском — не проблема: LLM переводит при генерации ответа, а поиск по ингредиентам делается по нормализованным названиям (маппинг русский → английский).

Для MVP берём Food.com (компактнее, есть теги и время готовки). RecipeNLG — резерв для расширения покрытия.

**Формат хранения:**

- **SQLite:** название, ингредиенты (список), шаги, время, теги. Используется для точного поиска по ингредиентам (FTS5).
- **ChromaDB:** векторные эмбеддинги рецептов (название + теги + описание). Используется для семантического поиска по сценарию.

**Зачем два вида поиска:**

Запрос «у меня курица и рис» — это поиск по ингредиентам (FTS5). Запрос «романтический ужин на двоих» или «быстрый белковый обед» — это поиск по смыслу, где нужны эмбеддинги. В реальном сценарии пользователь часто комбинирует: «у меня есть лосось, хочу что-то праздничное» — тогда результаты обоих поисков объединяются и ранжируются.

**Справочник цен (автообновляемый):**

- **Источник:** публичный веб-каталог Перекрёстка (perekrestok.ru/cat). Один источник — проще поддерживать, достаточно для оценки.
- **Механизм:** Python-скрипт (httpx + BeautifulSoup), парсит цены по фиксированному списку ~100 базовых продуктов (мясо, овощи, крупы, молочные, специи). Запуск: cron раз в 3 дня или вручную.
- **Хранение:** SQLite-таблица:
  ```
  prices (
      product_name TEXT PRIMARY KEY,
      price REAL,
      unit TEXT,
      updated_at TIMESTAMP
  )
  ```
- **Если цена не найдена** — бот пишет «цена неизвестна» для этого продукта, без выдумывания.

### 2.3 Интеграции и интерфейсы

- **Telegram Bot API** (aiogram) — основной интерфейс пользователя. Взаимодействие через long polling (для учебного проекта проще, чем webhook).
- **OpenAI API** — генерация ответов (GPT-4o-mini). Вызов по REST (HTTPS).
- **Скрипт парсинга цен** (httpx + BeautifulSoup), запуск по cron.
- **UI/UX в Telegram:** текстовые ответы с markdown-форматированием (жирный шрифт для названий рецептов, списки для ингредиентов). Inline-кнопки: 👍/👎 под каждым ответом, кнопка «Ещё варианты». Команды: `/start`, `/reset`, `/help`.
- **Логирование:** все запросы и ответы пишутся в SQLite (таблица `logs`: timestamp, chat_id, user_message, bot_response, feedback). Используется для ручного анализа качества.

### 2.4 Инфраструктура и развертывание

- **Стек:** Python 3.11+, FastAPI, aiogram, SQLite, ChromaDB, Docker.
- **Среды:** dev (локальный запуск, `.env.dev`) → prod (Docker-контейнер на VPS, `.env.prod`). Отдельной test-среды нет — тестируем локально.
- **Вычисления:** CPU, LLM через внешний API (OpenAI). Embedding-модель (~118MB) загружается при старте, работает на CPU.
- **Безопасность:** API-ключи в `.env`, не коммитятся (`.gitignore`). Из пользовательских данных храним только Telegram chat_id для ведения сессии.

## 3. Данные и качество знаний

Данные не содержат чувствительной информации — рецепты, ингредиенты, цены. Можно спокойно отправлять во внешний API.

### 3.1 Сбор и предобработка данных

- **Основной датасет:** [Food.com Recipes and Reviews](https://www.kaggle.com/datasets/irkaal/foodcom-recipes-and-reviews) (~80K рецептов, CSV).
- **Резервный:** [RecipeNLG](https://www.kaggle.com/datasets/paultimothymooney/recipenlg) (2M+ рецептов, CSV).
- **Предобработка:**
  - Маппинг русских названий ингредиентов → английские (для FTS-поиска по базе).
  - Фильтрация рецептов с неполными данными (нет ингредиентов или шагов).
  - Нормализация единиц измерения.
  - Обогащение метаданных: для каждого рецепта формируем текстовое описание (название + теги + ключевые ингредиенты) — оно идёт на вход embedding-модели.

### 3.2 Векторизация и индексирование

- **Embedding-модель:** `intfloat/multilingual-e5-small` (384 dims, multilingual, 118MB). Выбрана за поддержку русского и английского в одном пространстве — пользователь пишет на русском, рецепты на английском, модель проецирует их в общее пространство.
- **Индекс:** ChromaDB с persistent storage. Для ~80K рецептов индекс занимает ~200MB, строится за 5–10 минут на CPU.
- **Метрика:** cosine similarity.
- **Что индексируем:** конкатенация `name + tags + description` каждого рецепта. Это позволяет находить рецепты по запросам вроде «праздничный десерт», «здоровый обед», «comfort food на вечер».
- **Пересборка:** полная, при обновлении базы рецептов. При 80K записей — минуты, не проблема.

### 3.3 Метрики качества знаний

- **Покрытие:** Food.com содержит 80K рецептов — этого достаточно для большинства комбинаций продуктов. Проверим на 20–30 тестовых запросах.
- **Актуальность:** рецепты не устаревают. Цены обновляются раз в 3 дня.
- **Консистентность:** дубликаты в Food.com уже отфильтрованы авторами датасета.

## 4. Модель и генерация

### 4.1 Выбор LLM и промптинг

**Модель:** OpenAI GPT-4o-mini.

**Почему:** задача — сформулировать ответ на основе предоставленных рецептов и цен, не требуется сложное рассуждение. GPT-4o-mini стоит ~$0.15 / 1M input-токенов, что при среднем запросе ~2K токенов даёт ~$0.003 за запрос. Бюджета в $10–15 хватит на ~3000–5000 запросов.

**Промпт-шаблон (упрощённо):**

```
Ты — кулинарный помощник. Отвечай на русском.

Пользователь может:
- перечислить продукты → подбери рецепты из них (или с минимальной докупкой)
- описать ситуацию → подбери подходящие рецепты (свидание, спорт, быстрый обед и т.п.)
- комбинировать: продукты + ситуация

Для каждого рецепта укажи: название, ингредиенты, краткие шаги, время.
Если нужно докупить — укажи что и примерную стоимость из справочника.
Если цена неизвестна — так и напиши, не выдумывай.

Рецепты из базы (используй только их, не придумывай новые):
{retrieved_recipes}

Справочник цен:
{price_context}

Запрос пользователя: {user_query}
Продукты пользователя: {user_products}
История диалога: {chat_history}
```

**Ограничения:** max ~2000 токенов на ответ, температура 0.7.

### 4.2 Контроль качества ответов

- **Метрики (ручная оценка):**
  - Релевантность: предложенные рецепты реально можно приготовить из указанных продуктов.
  - Корректность цен: выборочная проверка 10–15 продуктов вручную.
  - Полезность: оценка 5–10 тестовыми пользователями (одногруппники).
- **Обработка ошибок:**
  - Если продуктов слишком мало — бот честно говорит об этом и предлагает докупить минимальный набор.
  - Если запрос не про еду — вежливый отказ: «Я кулинарный бот, давай поговорим о еде!»
  - Fallback: если LLM недоступен — возвращаем рецепты из базы без генерации.

### 4.3 Обучение/дообучение

Не предусмотрено в рамках учебного проекта. Используем модель as-is + prompt engineering.

## 5. UX / пользовательский опыт

### 5.1 Сценарии взаимодействия

**Основные:**

1. **Старт:** пользователь пишет `/start` → бот приветствует, объясняет что умеет.
2. **Поиск по продуктам:** «У меня курица, рис и соевый соус» → бот ищет по ингредиентам (FTS5), предлагает рецепты.
3. **Поиск по сценарию:** «Что приготовить на свидание?», «Лёгкий обед для спортивной недели», «Быстрый завтрак за 15 минут» → бот ищет семантически (ChromaDB), предлагает подходящие рецепты.
4. **Комбинированный:** «У меня есть лосось, хочу что-то праздничное» → FTS5 фильтрует по ингредиенту, ChromaDB ранжирует по сценарию.
5. **Уточнение:** «А что-нибудь попроще?», «Без духовки» → бот адаптирует выдачу в рамках контекста.
6. **Расчёт стоимости:** «Сколько будет стоить докупить для борща?» → бот считает по справочнику цен.

**Исключительные:**

- Пользователь ввёл бессмыслицу → бот просит уточнить.
- Пользователь спрашивает не про еду → вежливый редирект.
- LLM API не отвечает → fallback-сообщение + рецепт из базы.

### 5.2 Диалоговая логика

- **Multi-turn:** бот помнит контекст в рамках сессии (последние 10 сообщений, список продуктов). Хранение в памяти (dict по chat_id), сброс по `/reset` или через 30 минут неактивности.
- **Тон:** нейтральный, по делу. Без избыточного юмора — пользователь пришёл за рецептом, а не за шутками.

### 5.3 Метрики UX

- Время ответа: целевое < 15 секунд.
- Сбор обратной связи: кнопки 👍/👎 под ответом бота.
- Логирование: все диалоги сохраняются для ручного анализа качества.

## 6. Безопасность, соответствие и этика

- **Персональные данные:** храним только Telegram chat_id — ФИО, номера телефонов не собираем. Логи диалогов не содержат персональных данных. Учебный проект — ФЗ-152 формально не применим, но принцип минимизации данных соблюдаем.
- **Фильтрация контента:** бот ограничен кулинарной тематикой через system prompt. Запросы не по теме отклоняются. Промпт содержит явную инструкцию не генерировать вредоносный, оскорбительный или не относящийся к еде контент.
- **Прозрачность:** в приветственном сообщении `/start` явно указано, что это бот на базе LLM, ответы могут быть неточными, цены ориентировочные.

### 7.2 Поддержка и эксплуатация

- **Поддержка:** силами команды на время курса. После сдачи проект остаётся как open-source без активной поддержки.
- **Мониторинг:** ручной просмотр таблицы `logs` в SQLite — анализ частых запросов, ошибок, фидбэка (👍/👎).
- **Обновление знаний:** база рецептов статична (Food.com). Цены обновляются cron-скриптом раз в 3 дня.
- **Метрики эксплуатации:** latency (время ответа из логов), cost per session (трекинг использования токенов OpenAI через API usage).

## 8. Риски и допущения


| Риск | Вероятность | Влияние | Митигация |
| --- | --- | --- | --- |
| LLM галлюцинирует несуществующие рецепты | Средняя | Среднее | Подаём реальные рецепты из базы в контекст промпта, LLM только форматирует и адаптирует |
| Парсинг цен сломался (Перекрёсток поменял вёрстку) | Средняя | Низкое | Сохраняем последнюю известную цену, пишем в лог. Если не починить — ручное обновление CSV |
| Бюджет на OpenAI API закончился | Низкая | Высокое | Лимит 20 запросов/день на пользователя. ~$10–15 хватит на 3000–5000 запросов |
| Пользователь вводит продукты в непредсказуемом формате | Высокая | Среднее | LLM сам извлекает сущности из свободного текста — это его сильная сторона |
| Рецепты на английском, а пользователь на русском | Высокая | Среднее | Маппинг ингредиентов ru→en для FTS; multilingual embedding для векторного поиска; LLM переводит при генерации |
| Семантический поиск выдаёт нерелевантные рецепты | Средняя | Среднее | Ручная проверка на 20–30 тестовых запросах; при низком качестве — добавление фильтра по тегам поверх vector search |

**Непроверенные допущения:**
- Multilingual embedding (`intfloat/multilingual-e5-small`) достаточно хорошо проецирует русские запросы и английские рецепты в общее пространство — нужно проверить на тестовых примерах.
- 80K рецептов Food.com покрывают типичные запросы русскоязычных пользователей — возможно, часть рецептов будет нерелевантна (американская кухня преобладает).
- Перекрёсток не блокирует парсинг каталога — нужно проверить на этапе MVP.


## 9. Бюджет и ресурсы

- **Команда:** 2 человека (Новгородский Андрей, Бузмаков Василий).
- **LLM API:** OpenAI, ~$10–15 на проект.
- **Хранение:** SQLite (бесплатно, без внешних зависимостей).
- **Хостинг:** бесплатный VPS или локальный запуск для демо.

## 10. Приложения

### Словарь терминов

| Термин | Описание |
| --- | --- |
| LLM | Large Language Model — большая языковая модель |
| RAG | Retrieval-Augmented Generation — генерация ответа с подкреплением поиском по базе знаний |
| FTS5 | Full-Text Search 5 — модуль полнотекстового поиска в SQLite |
| Embedding | Векторное представление текста в числовом пространстве для семантического сравнения |
| Cosine similarity | Метрика близости двух векторов (от -1 до 1), используется для ранжирования результатов поиска |
| Fallback | Запасной вариант поведения при сбое основного компонента |
| Multi-turn | Многоходовый диалог с сохранением контекста между сообщениями |
